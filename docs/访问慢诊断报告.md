# 访问不可达/极慢问题 · 诊断报告

**日期**：2026-10-14
**上报现象**：鸿蒙手机访问不通；同一时段 PythonAnywhere 管理页也访问超时
**诊断结论**：**跨境链路质量问题，非应用故障、非服务器宕机**

---

## 一、结论先行

| 判断项 | 结果 | 依据 |
|---|---|---|
| 服务器是否宕机 | ❌ 否 | 境外实测 HTTP 200，延迟 219ms，丢包 0% |
| 应用是否有故障 | ❌ 否 | 所有接口均返回 200，无 5xx |
| 域名是否解析异常 | ❌ 否 | 三个域名解析稳定，无解析失败 |
| **跨境链路是否劣化** | ✅ **是** | 路径经中国电信国际出口，跨境段超时 |
| **前端资源策略是否合理** | ⚠️ **存在明显浪费** | 首页 85KB 明文传、禁用了缓存 |

**一句话**：服务器是好的，是**从大陆到美国的这条国际链路在波动**，加上前端每次都全量重传未压缩的 85KB，把链路波动放大成了「打不开」。

---

## 二、为什么能确定是链路问题

### 证据 1：同一时刻，境外访问完全正常

```
首页:    HTTP 200   总耗时 1.46s
管理页:  HTTP 200   总耗时 1.35s
TCP 443: 可达
Ping:    5 包全收, 丢包 0%, 平均 219ms
```

服务器活着，服务在正常工作。

### 证据 2：三个域名指向同一个 IP —— 单点无冗余

```
kiviwang.pythonanywhere.com  -> 35.173.69.207
www.pythonanywhere.com       -> 35.173.69.207
pythonanywhere.com           -> 35.173.69.207
```

**应用和管理页共用同一个入口 IP。** 这直接解释了「为什么连管理页也进不去」——
不是应用出问题，而是这一个入口的链路同时劣化了。
只要这条路径堵住，**应用、管理页、所有 PythonAnywhere 服务会一起不可用**。

### 证据 3：网络路径经过国际出口，跨境段超时

```
 6  10.200.46.253     2.8 ms
 7  36.110.203.141    4.2 ms   ← 中国电信骨干网
 8  36.110.255.245    5.2 ms   ← 中国电信骨干网
 9  *                           ← 超时
11  202.97.43.110   272.5 ms   ← 中国电信国际出口 AS4134
12  218.30.53.150   147.5 ms   ← 跨境后
13  *                           ← 超时
```

延迟从 **5ms 直接跳到 272ms**，且第 9 跳后大量超时。
这段「电信骨干 → 国际出口 → 美国 AWS」正是**最拥塞、最不稳定**的环节。

### 证据 4：服务器在美国东部

```
IP:        35.173.69.207
主机名:    ec2-35-173-69-207.compute-1.amazonaws.com
位置:      Ashburn, Virginia, US
运营商:    AS14618 Amazon.com, Inc.
```

中国到美东，跨境距离最远的路径之一。

### 证据 5：抖动已经很明显（还是在境外测的）

连续 8 次请求同一页面：

| 次数 | 总耗时 | TLS 握手 |
|---|---|---|
| 1 | 1.58s | 0.50s |
| 2 | 1.45s | 0.59s |
| 3 | 1.39s | 0.52s |
| 4 | **1.08s** | 0.44s |
| 5 | **2.75s** | **1.66s** ← 抖动 2.5 倍 |
| 6 | 1.29s | 0.42s |
| 7 | 1.96s | 0.44s |
| 8 | 1.13s | 0.45s |

**境外都有 2.5 倍抖动**，跨境到大陆会成倍放大。
第 5 次 TLS 握手 1.66 秒，是正常值的 3.5 倍 —— 典型的重传特征。

## 三、前端放大效应（可优化项）

实测首页响应头：

```
Content-Length: 85233
Cache-Control:  no-cache, must-revalidate      ← 每次都重新下载
（无 Content-Encoding）                          ← 未启用 gzip
Server: PythonAnywhere
```

### 两个问题

**问题 1：完全没启用 gzip 压缩**

85KB 的 HTML 以**明文**传输。这类文本压缩率通常 70~80%，
启用 gzip 后应该只有 **15~25KB**。

在跨境链路上，85KB vs 20KB 的差距，可能就是 3 秒 vs 1 秒。

**问题 2：禁止了缓存**

`Cache-Control: no-cache, must-revalidate` 意味着：
**每次打开网站都要完整重下 85KB**，哪怕内容一个字节都没变。

孩子的日常用法（每天打开、反复刷题）正好命中这个最差情况。

### 放大机制

```
链路抖动 (TLS 反复重传)
      ×
每次必须重下 85KB 未压缩内容
      =
表现为「有内容但很慢」甚至「打不开」
```

这解释了你描述的**「页面有内容但很慢」**——请求通了，但传输过程被拖长。

## 四、为什么表现是「时好时坏」

跨境出口是**共享带宽、按小时波动**的。这解释了全部历史现象：

| 现象 | 真实原因 |
|---|---|
| 鸿蒙秒开、苹果不通 | 不是系统差异，是**两者走了不同的解析/连接路径**，或测试时刻不同 |
| Reload 后 5-10 分钟不通，之后自己好 | **恰好撞上链路拥塞窗口**，与 Reload 无因果关系 |
| 早上能用、晚上不行 | 晚高峰国际出口拥塞 |
| 现在连管理页都超时 | 整个入口 IP 的链路都在受影响 |

> 补充说明：之前把「Safari 无响应」归因到客户端并加了自动重试，
> 从当时的日志看是合理的（确实有请求挂起）。
> 现在有了更完整的证据，**主因应修正为跨境链路**，
> 自动重试仍然有效，但只是缓解手段，不是根治。

## 五、可选方案对比

| 方案 | 根治程度 | 成本 | 见效速度 | 适合场景 |
|---|---|---|---|---|
| **A. 前端传输优化**（gzip + 缓存 + 资源内联） | 缓解 | ¥0 | 今天 | 先止血，立即见效 |
| **B. 加 Cloudflare 代理** | 部分根治 | ¥0（免费版） | 1 天 | 想保留现有部署 |
| **C. 迁移到国内/香港托管** | 根治 | ¥50~200/月 | 3~7 天 | 长期稳定 |
| **D. 备用线路双活** | 部分根治 | ¥0~100/月 | 1~2 天 | 不能停机 |

### 方案 A：前端传输优化（建议先做）

**做什么**：
1. 启用 gzip 压缩（85KB → 约 20KB）
2. 静态资源加长效缓存，HTML 用 ETag 协商缓存
3. 关键 CSS/JS 内联，减少往返次数

**预期效果**：首屏传输量降 **70%+**，弱网下明显改善
**风险**：低。纯前端/服务端配置，不动业务逻辑
**局限**：链路本身波动时仍会慢，只是「不至于打不开」

### 方案 B：Cloudflare 代理（性价比高）

在现有部署前加一层 Cloudflare：
- 静态资源走 Cloudflare 全球边缘缓存，**大陆附近节点直接命中**
- 动态请求仍回源美东，但 TLS 握手走就近节点，**省掉最贵的跨境握手**
- 免费版可用，不用改代码，只需改 DNS

**注意**：Cloudflare 免费版在大陆访问质量也一般，但通常**比直连美东好**。

### 方案 C：迁移托管（根治）

迁到国内云或香港节点：
- **香港**：跨境但距离近，延迟可从 220ms 降到 30~50ms，且基本无出口拥塞
- **国内云**：最快，但需备案（面向个人学习用途，流程较繁琐）

**推荐香港轻量云**：延迟低、免备案、成本可控（约 ¥60~100/月）。

## 六·补充、方案 A 已实施（2026-10-14）

### 做了什么

| 优化项 | 说明 |
|---|---|
| **gzip 压缩** | 对 HTML/JSON/JS/CSS/SVG 文本响应启用 gzip（level 6），零第三方依赖 |
| **静态页缓存** | `/`、`/admin` 由 `no-cache` 改为 `max-age=600` + ETag 协商缓存 |
| **接口禁缓存** | `/api/*` 保持 `no-store`（数据实时性），但仍享受 gzip |
| **Vary 头** | 明确 `Accept-Encoding`，避免中间缓存串味 |
| **首屏先绘制** | 把初始化推迟到首屏绘制后（`requestIdleCallback`），避免 52KB JS 阻塞 |
| **登录路径加固** | 登录/注册/匿名原来用裸 `fetch`（无超时无重试），改走带超时+重试的封装，并在 4 秒后提示「网络较慢，正在重试…」 |

### 实测效果（浏览器端真实传输量）

| 资源 | 优化前 | 优化后 | 降幅 |
|---|---|---|---|
| 首页 HTML | 85,233 B | **26,348 B** | **-69%** |
| 课程列表 API | 12,694 B | 2,636 B | -79% |
| 课程详情 API | 37,463 B | 8,457 B | -77% |
| **重复访问首页** | 85,233 B | **0 B（304）** | **-100%** |

### 预期收益

- **首次打开**：跨境传输量降到约 1/3，弱网下白屏时间显著缩短
- **日常刷题**（高频重访）：命中本地缓存或 304，**几乎零传输**
- **链路拥塞时**：登录等关键操作最多等 12 秒即重试，不再无限转圈

### 验证

- 全量回归 **521/521 通过**（含 28 项新增性能测试）
- 浏览器实测：gzip 生效、无 JS 报错、登录/注册/匿名/课程列表功能正常

### 说明

> 这一层是**缓解**，不是根治。跨境链路本身波动时（例如你遇到的持续约 5 分钟不通），
> 页面仍可能短暂打不开 —— 但传输量降到 1/3 后，能通过的窗口会明显变多、变宽。
> 若测试下来仍不够，再走第 3 步迁香港。

## 七、需要你配合确认的事项

为了进一步定位，下次再遇到访问不通时，麻烦记录：

1. **具体表现**：转圈超时 / 秒报错 / 能开但慢
   → 区分「不可达」与「极慢」

2. **发生时段与持续时长**：大致几点、持续多久
   → 你已反馈「约 5 分钟后自己恢复」，这与**链路临时拥塞/TCP 重传退避**的特征吻合

3. **切换网络测试**：联通/电信流量 vs 家里 Wi-Fi，是否一方好一方坏
   → 能确认是「单个运营商出口」还是「通用跨境」问题

4. **是否只影响本应用**：同时能否打开其他国外网站（如 github.com）
   → 区分「链路问题」与「服务器问题」
